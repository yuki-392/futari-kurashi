# 世帯・招待の権限表と検証

対象はPhase 1・項目4。[実装記録0006](./implementation-log/0006-firestore-permissions.md)に理由・修正・結果を残します。この文書は項目4のローカル検証と権限表を記録しています。項目5で同じRulesをクラウドへ反映・ソース照合済みです。iPhone＋Mac／Chromeでの共有確認も本人確認済みです（[記録0007](./implementation-log/0007-realtime-sharing.md)）。

## 前提と登場人物

正常な2人世帯A・Bと、招待発行中の1人世帯Pをテスト専用に用意します。「作成者」「参加者」は世帯Aのメンバー、「他世帯」はB、「招待作成者」はP、「招待対象者」はPの招待先メールを確認済みの未所属ユーザーです。未確認ユーザーは作成者と同じUIDでもメール未確認、未認証ユーザーは認証なしです。

所属と招待の作成は関連文書との原子的操作が前提です。単独での作成を許可する意味ではありません。新しい世帯の作成は、メール確認済み・未所属の本人だけが行えます。

## 作成・更新・削除

| 操作                                                 | 許可される人・条件                                            | その他 |
| ---------------------------------------------------- | ------------------------------------------------------------- | ------ |
| 世帯と本人所属の新規作成                             | メール確認済み・未所属の本人が一括作成                        | 拒否   |
| 招待作成と有効招待IDの設定                           | 1人世帯の作成者が一括作成                                     | 拒否   |
| 招待の取消・再発行                                   | 1人世帯の作成者。再発行は新規招待を一括作成                   | 拒否   |
| 招待消費・本人所属作成・メンバー追加                 | 有効な招待先の確認済みメール本人、未所属、2人目として一括更新 | 拒否   |
| 既存の所属先・所有者・世帯名・任意のメンバーIDの変更 | なし                                                          | 拒否   |
| 招待先・作成者・発行時刻の変更                       | なし                                                          | 拒否   |
| 所属・世帯・招待の削除                               | なし                                                          | 拒否   |

メール未確認・未認証は全書き込みを拒否します。作成者・参加者・他世帯のIDが分かっていても、権限は増えません。未知の項目・不正な型・必須項目欠落・作成時刻の偽装を拒否します。既存の正常データをそのまま書く操作すべての禁止を意味するものではなく、許可された状態遷移とデータ整合性を検証します。

## 未実装パス

項目4当時はtasksも全拒否でした。現在のtasksと繰り返し定義/履歴は下記の項目7/8A/8Bの権限を適用します。cleaningSchedules、shoppingItems、declutterItems、expenses、incomes、budgets、houseRulesと未知のパスについては、全立場から単体取得・一覧・検索・作成・更新・削除を拒否します。自分の世帯内でも同様です。各機能を追加するときに専用Rulesとテストを実装します。

## 拒否と競合の確認方法

- 拒否では単なる例外でなく`permission-denied`を確認し、書き込み前後の所属・世帯・招待と、対象の未実装文書を比較します。
- 原子的更新の分解、別世帯の招待/所属/メンバーを混ぜた操作を拒否し、部分保存がないことを確認します。
- 招待確認後の期限切れ・取消・再発行でも参加できません。期限切れはテスト専用データの発行時刻を調整し、Rulesを通した参加を試します。
- 同時作成・同一招待への同時参加・同一ユーザーの2世帯への同時参加は、1件だけ成功します。敗者は権限拒否となり、所属とメンバー・招待消費が一致します。
- 取消/再発行と参加の競合は、どちらが先に成立しても整合することを確認します。参加が先なら取消/再発行を拒否し、取消/再発行が先なら旧招待による参加を拒否します。

## 実行方法と限界

```sh
nvm use
npm run test:rules
npm run check
npm run test:integration
```

JDK・Emulatorの準備は[世帯検証手順](./household-verification.md)を参照してください。既存CIの`test:integration`が拡張したRulesテストも実行します。権限を無効にしたSDKは、架空データの準備・結果確認だけに使用します。検証操作はすべて通常のクライアントSDKです。

この検証はSecurity Rulesの範囲です。管理者SDK/IAMの保護や、実クラウド・実端末での動作を検証済みとは扱いません。

## 項目7: ToDoの追加権限

households/{世帯}/tasks/{ToDo}だけを追加許可する。既存の所属/世帯/招待とその他パスの拒否は維持する。

| 操作                         | 確認済み同世帯の2人                                                  | 他世帯・未所属・未確認・未認証 |
| ---------------------------- | -------------------------------------------------------------------- | ------------------------------ |
| 単体取得                     | 許可                                                                 | 拒否                           |
| 上限付きの世帯内一覧         | 許可                                                                 | 拒否                           |
| 無制限一覧・collection group | 拒否                                                                 | 拒否                           |
| 作成                         | スキーマ・担当・サーバー時刻・本人作成・初期版1/未完了を満たせば許可 | 拒否                           |
| 更新                         | 作成情報を維持・更新者本人・サーバー時刻・版+1で許可                 | 拒否                           |
| 削除                         | 担当に関係なく許可。UI/サービスはtransactionで期待版も照合           | 拒否                           |

## 項目8A: 繰り返し定義・履歴

| 操作                                      | 確認済み同世帯の2人                                                        | それ以外 |
| ----------------------------------------- | -------------------------------------------------------------------------- | -------- |
| 定義/履歴get・上限付きlist                | 許可                                                                       | 拒否     |
| 無制限list・collection group              | 拒否                                                                       | 拒否     |
| 定義作成/設定編集/停止/再開               | スキーマ・周期・担当・版・監査・操作種別を満たす場合のみ                   | 拒否     |

## 項目8B：掃除と担当交代

同世帯の確認済みメンバーだけが既存の繰り返し定義/履歴へアクセスする。新しいパスは増やさず、cleaningSchedules等の未実装パスの拒否も維持する。

| 操作            | 許可条件                                                   | 拒否する例                                                               |
| --------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| 定義の追加/編集 | 旧形式または整合する区分/場所/交代設定、新形式の項目は保持 | 部分的追加/項目欠落、不正な場所/型/区分、1人世帯や未担当/2人担当での交代 |
| 掃除一覧        | 確認済み所属者、上限指定、区分/稼働/期日/任意の場所条件    | 他世帯・未所属・未確認・未認証、上限なし                                 |
| 完了/担当交代   | 定義/履歴の原子的更新、完了前担当以外の世帯メンバーへ変更  | 交代漏れ、実行者による順序変更、別UID、履歴snapshot改ざん、単独書き込み  |
| 取消            | 直近参照/版の一致、履歴の担当・予定へ原子的復元            | 担当を戻さない、古い履歴、設定変更後の取消、履歴内容の編集/削除          |

Rulesの日付計算は定義更新側に集約し、履歴は更新前後の版・操作・参照・snapshot・次回日付を照合する。評価1000式上限への対応理由は記録0011 D6を参照。旧形式/新形式の月末と不正日付もEmulatorで検証する。

掃除の追加検証は27正常/57拒否。既存22シナリオ（追加29正常/697拒否）、ToDo13正常/66拒否、繰り返し31正常/90拒否も維持して成功。クラウドRulesは項目8B版を反映し、ソース一致を読み戻し確認した。
