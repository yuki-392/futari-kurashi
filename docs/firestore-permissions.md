# 世帯・招待の権限表と検証

対象はPhase 1・項目4。[実装記録0006](./implementation-log/0006-firestore-permissions.md)に理由・修正・結果を残します。この文書は項目4のローカル検証と権限表を記録しています。項目5で同じRulesをクラウドへ反映・ソース照合済みです。iPhone＋Mac／Chromeでの共有確認も本人確認済みです（[記録0007](./implementation-log/0007-realtime-sharing.md)）。

## 前提と登場人物

正常な2人世帯A・Bと、招待発行中の1人世帯Pをテスト専用に用意します。「作成者」「参加者」は世帯Aのメンバー、「他世帯」はB、「招待作成者」はP、「招待対象者」はPの招待先メールを確認済みの未所属ユーザーです。未確認ユーザーは作成者と同じUIDでもメール未確認、未認証ユーザーは認証なしです。

所属と招待の作成は関連文書との原子的操作が前提です。単独での作成を許可する意味ではありません。新しい世帯の作成は、メール確認済み・未所属の本人だけが行えます。

## 拒否と競合の確認方法

- 拒否では単なる例外でなく`permission-denied`を確認し、書き込み前後の所属・世帯・招待と、対象の未実装文書を比較します。
- 原子的更新の分解、別世帯の招待/所属/メンバーを混ぜた操作を拒否し、部分保存がないことを確認します。
- 招待確認後の期限切れ・取消・再発行でも参加できません。期限切れはテスト専用データの発行時刻を調整し、Rulesを通した参加を試します。
- 同時作成・同一招待への同時参加・同一ユーザーの2世帯への同時参加は、1件だけ成功します。敗者は権限拒否となり、所属とメンバー・招待消費が一致します。
- 取消/再発行と参加の競合は、どちらが先に成立しても整合することを確認します。参加が先なら取消/再発行を拒否し、取消/再発行が先なら旧招待による参加を拒否します。

対象はhouseholds/{hid}/declutterItems/{id}。UIの所有者にかかわらず、確認済み同世帯メンバーのどちらも操作できる。所属・招待・通常ToDo・繰り返し/掃除・買い物の既存権限は変更しない。

| 立場                                 | 単体取得 | 上限付き一覧/方法・期限クエリ | 作成                     | 編集・完了・解除           | 削除 |

| 他世帯・未所属・メール未確認・未認証 | 拒否     | 拒否                          | 拒否                     | 拒否                       | 拒否 |

世帯を横断するcollectionGroupと無制限一覧は拒否。新規は未処分・completedAt/Byともnull。品名1〜100文字、方法の列挙、重複のない現在メンバーのownerIds、実在日、dueDate/nullとsortDueDate/`~`の一致、全必須/余分な項目・型・監査を検証する。

| 状態遷移          | 完了監査と条件                                          |
| ----------------- | ------------------------------------------------------- |
| 未処分→未処分     | completedAt/Byともnull                                  |
| 未処分→処分済み   | 保留以外。completedAt=request.time、completedBy=認証UID |

| 無制限一覧・上限超過・未知フィールド・監査改ざん   | 拒否                                                                      | 拒否                           |

直接SDKの予算テストは7正常/65拒否（初回ローカル検証時）。拒否後の保存内容不変性、同じ版の競合の敗者理由と保存後の版/監査、アーカイブ予算の取得/解除を検証する。budgetsを一般の未実装拒否表から専用テストへ移し、既存22世帯シナリオの追加拒否は505→457（48件移管）。他の未実装パス拒否は維持する。家計の旧不変性ヘルパーは`withSecurityRulesDisabled`の返り値を利用していたため、外部変数で実際の文書を捕捉する形に修正し、既存の拒否前後比較を再検証した。

## Phase 2・項目3: 支出の精算情報・月状態・精算金

確認済み同世帯メンバーだけが対象。未認証・未確認メール・未所属・他世帯の全操作を拒否する。下記以外のパス拒否も維持する。

| 操作                         | 同世帯の許可条件                                                                 | 拒否する例                                                |
| ---------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 支出取得・一覧               | 既存の上限付き取得                                                               | 無制限一覧・他世帯                                        |
| 精算対象支出の作成/編集/削除 | 月状態と同時更新、既存の明細検証も維持                                           | 月状態なし、月移動の片側だけ、旧クライアントのsharing消失 |
| 支払者・割合                 | 現在の2人のUID、整数0〜100%、合計100%                                            | 第三者、1人世帯の精算対象、小数・負数・余分なUID          |
| 月状態/精算金の取得・一覧    | 単体またはlimit 1〜10000                                                         | 無制限・超過・他世帯                                      |
| 月状態の作成/更新            | 決定的な月ID、版+1、監査、参照先の同時変更とnetPaid整合                          | 任意の累計、過去の版、参照先の混在、時刻偽装              |
| 精算金の作成                 | 本人監査、正の整数円、同世帯2人の異なる送金者/受取者、実在日、月状態と原子的更新 | 単独作成、0円・小数、別月の状態更新、監査改ざん           |
| 精算金の取消                 | 未取消だけ、取消者/サーバー時刻、版+1、月累計の逆更新                            | 金額/支払日/作成情報の変更、再取消、単独取消              |
| 月状態/精算金の削除          | 許可しない                                                                       | 所属者による削除も拒否                                    |

旧支出はsharingなしで引き続き読み書き可能、nullは明示的な対象外。旧支出・対象外の変更は月状態を増やさない。新形式から旧形式への消失は拒否する。拒否テストは関連3コレクションを読み戻し不変性を確認する。競合では成功件数、敗者のpermission-denied、月状態・精算金・支出の整合を確認する。[記録0020](./implementation-log/0020-settlements.md)を参照。
