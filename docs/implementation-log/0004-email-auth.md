## 目的と実装前の方針

承認済み計画に沿い、登録・メール確認・ログイン・ログアウト・パスワード再設定を提供する。世帯共有、Firestoreのクラウド設定、本番公開には進まない。

## 判断と理由

### D1: 認証状態をProviderに集約する

初期確認中・未ログイン・未確認メール・ログイン済み・初期化エラーを区別し、メール確認前に共有準備画面を表示しない。各画面で個別に認証判定する代案に比べ、判定漏れと初期画面のちらつきを避けられる。購読解除と再試行が必要になる。

### D2: AuthとFirestoreの初期化を分離する

今回は認証だけを必要とするため、Firestoreの取得を遅延する。既存のgetFirebaseServicesの戻り値は維持し、アプリとAuthを共有する。Authの永続保存はSDKに任せ、パスワードは保存しない。

### D3: Firebase標準のメール操作とポリシーを使う

確認・再設定は標準のメールとアクションページを使い、専用サーバーや独自トークンを追加しない。最低12文字・文字種強制なしをFirebase側でも強制し、列挙保護を有効にする。メール送信の失敗とアカウント作成成功を区別し、再送で回復できるようにする。

### D4: 実アカウントへのメールは本人操作で確認する

自動テストはAuth Emulatorの架空アカウントとメール確認コードを使う。実機はユーザーがパスワード入力・受信メール操作を行い、コード・パスワードを記録しない。実機結果が残る場合は確認待ちとする。

## 指摘と対応

### R1: 新規登録ボタンを押せない

- ユーザーの指摘（原文）: 「新規登録画面の登録するボタンが押せない」
- 対象: D1、`AuthPanel.tsx`の登録フォーム・入力検証・処理中制御。
- 対応状態: 修正後の登録成功をユーザー確認済み。今回のiPhoneで発生した直接の原因は未確定のまま。
- 調査方針: 既存のEmulator登録テストを再実行し、ブラウザーの入力チェックと画面内メッセージ、二重送信防止を切り分ける。確認できた原因に対し、失敗する回帰テストを追加して修正する。
- 検証予定: 対象の回帰テスト、`npm run check`、Auth Emulatorでのブラウザー操作。PWAに影響する場合は既存PWAテストも実行し、検証公開後の実機結果を別に記録する。
- 追加回答（原文）: 「押しても反応がない」。通常入力の既存Emulatorテストは再実行でも成功した。
- 確認できた問題: 未入力時はブラウザーの必須チェックがsubmitを止め、アプリ内の案内が出ない。また入力イベントなしでDOM値のみ変わる状態では、React stateの旧値で検証してしまう。いずれも追加テストが修正前に失敗した。今回のiPhoneでどちらが発生したかは未確定。
- 修正方針: フォームの現在値を送信時に取得し、検証をアプリ内で統一する。エラーを送信ボタンの近くに表示し、フォーカスを移して画面外の案内を見落としにくくする。必須入力・12文字・確認一致・二重送信防止は維持する。
- 実際の修正: `AuthPanel.tsx`で`FormData`を使い、入力の`name`を追加。`noValidate`でブラウザー固有の表示だけに依存する検証をやめ、登録・ログイン・再設定の必須/形式チェックをアプリ内で行う。`validation.ts`に共通メール検証と確認用パスワードの未入力案内を追加。エラーはボタンの直前に表示しフォーカスを移す。
- 再検証: 回帰テスト2件の失敗→成功を確認。ログイン/再設定の不備も含めVitest全34件と`npm run check`が成功。Emulator/Chromium（390×844）で未入力・短いパスワード・確認未入力・不一致の案内とフォーカス/表示領域、自動入力を想定したイベントなしのDOM値取得、その後の登録・メール確認・永続保存・ログアウト・再設定が成功。キャプチャも確認済み。OSの自動入力自体と実機での解消はまだ未確認。
- PWA回帰検証: `npm run test:pwa`が成功。静的キャッシュ・オフライン・更新延期・再通知・更新適用を維持。
- 修正版公開: 同じ`pwa-check`へ`auth-check-fix1`を公開。Hostingバージョン`cb54d6c7421fd398`、有効期限は**2026-10-26 13:46（日本時間）**（`2026-10-26T04:46:38.653922457Z`）。上記公開コマンドの識別子だけを変更し、プロジェクトID・7日・`--no-authorized-domains`を維持した。Auth設定・Firestore・本番チャネルは変更なし。
- 公開先の確認: Chromium 390×844で`auth-check-fix1`、未入力での案内表示・フォーカス・画面内表示を確認。登録リクエスト0件、実行エラー0件。実アカウント作成・メール送信は行っていない。

### R2: 確認メールが届かない

- ユーザーの指摘（原文）: 「確認メールがこない」
- 画面の表示（本人回答）: 「確認メールを送りました」
- 対象: D3の確認メール送信とD4の実メール検証。
- 対応状態: 解消・本人確認済み。ユーザーが迷惑メール内で確認メールを発見。送信失敗ではなく、今回のメールは迷惑メールに分類されていた。
- 調査方針: 送信コード、専用プロジェクトのメール配信/テンプレート設定、Firebase公式の障害情報を読み取りで確認する。実メールの再送は本人が行い、アカウントの作り直しや確認済みフラグの手動変更は行わない。
- 確認方法: API設定の取得と公式資料を確認し、本人に迷惑メール・表示された宛先の一致・必要なら1回の再送を案内する。コード・パスワード・メール本文は記録しない。
- 調査結果: コードは`sendEmailVerification`の成功後にのみ送信成功を表示する。専用プロジェクトの設定は`sendEmail.method: DEFAULT`、確認テンプレートの送信元ローカル部は`noreply`、HTML形式、独自SMTPなし。メール/パスワードは有効で、設定不足は今回の読み取りでは見つからなかった。Firebase公式Status Dashboardの取得時点では「No incidents」。個別メールの配達成功や未着原因はこれらから判断できない。
- 次の確認: 画面上の宛先が本人のメールと一致するか、迷惑メール/すべてのメールで`futari-kurashi-5fcab9`や`noreply`を検索し、見つからなければ本人が「確認メールを再送」を1回押す。まだ届かない場合は再送後の表示とメールサービス名だけを確認する。
- 今回の変更: 調査内容を本記録と検証手順に追記。原因未確定のため認証コード・Firebase設定・公開版は変更していない。確認済みフラグの手動変更、実メールの自動再送も行っていない。
- 参照: [Firebaseの確認メール送信](https://firebase.google.com/docs/auth/web/manage-users#send_a_user_a_verification_email)、[公式障害情報](https://status.firebase.google.com/)。文書のみの変更のため整形チェックを行い、コードの再テストは不要と判断。
