## 記録する単位

- 機能追加・不具合修正・設計変更・設定変更・依存関係更新など、レビューできる作業単位で1ファイル作成します。
- Phase全体を1ファイルにまとめず、認証、世帯への招待、買い物リストなど、判断と変更を追える大きさに分けます。
- 同じ作業中の小さな修正は同じ記録に追記します。完了後の独立した修正は新しい記録を作り、元の記録と相互にリンクします。
- 文書だけの変更も記録します。小さな変更は理由・変更箇所・検証を短く記載し、不要な欄は「該当なし」とします。
- ファイル名は`0003-short-description.md`のように連番と内容が分かる名前にします。日付は日本時間です。番号は再利用しません。

## Codexの作業手順

1. **着手前:** この一覧と関連する過去の記録を読み、未対応の指摘・変更済みの判断を確認します。[テンプレート](./TEMPLATE.md)から新しい記録を作り、目的、対象要件、実装予定、判断理由、確認方法を記載します。チャットでも今回の方針を短く説明します。
2. **実装中:** 方針が変わったら、変わった理由と影響を記載します。元の判断を消さず、「変更済み」と新しい判断へのリンクを残します。
3. **実装後:** 実際に変更したファイル・動作、実行した検証と結果、未検証・未解決事項を追記します。予定を実績として書かず、一覧の状態と関連ドキュメントも更新します。
4. **報告時:** チャットの完了報告に実装記録のリンクと、ユーザーが確認するとよい点を添えます。
5. **指摘を受けたら:** 指摘を記録し、該当する仕様・コード・テストを確認して対応します。指摘内容、採用/見送りの理由、修正、再検証、残る確認事項を追記します。

通常の実装に毎回承認待ちを追加する運用ではありません。ユーザーから「実装前に確認したい」などの指定がある場合は、その指定に従います。

## 指摘する方法

チャットで、例えば次のように伝えてください。

> 0003のD1について、招待はメールではなくURLで共有したい。
>
> 0004の「実際の変更」にある完了時の削除は困る。履歴を残してほしい。

番号がなくてもCodexが該当記録を特定します。Markdownを直接編集して「指摘と対応」に追記する方法も使えます。Codexは既存の指摘を消したり、内容を変えたりしません。

ユーザー確認は「未確認」「指摘あり」「確認済み」で管理し、「確認済み」はユーザーが明示的に確認した場合だけ記載します。テスト成功や返信がないことを、ユーザーの承認として扱いません。修正を実装した状態と、ユーザーが修正を確認した状態も区別します。

## 記録の書き方

- 判断には`D1`、指摘には`R1`のように、そのファイル内で固定の番号を付けます。
- なぜ必要か、選択理由、現実的な代案、制約・不利益を簡潔に説明します。単に「ベストプラクティスだから」で済ませず、このアプリの要件との関係を書きます。
- 前提、確認できた事実、未確定事項を区別します。未実行のテストや未確認の外部情報を根拠にしません。
- 関連する仕様の見出しと、実装ファイル・関数などへの参照を残します。コミット済みの場合は実際のコミットIDやPRリンクを追記できます。記録のためだけにコミット・pushする必要はありません。
- 秘密鍵・パスワード・トークン・個人の生活データを記録しません。
- 製品の要件は[製品仕様](../product-spec.md)、現在の設計は[設計方針](../architecture.md)、進捗は[開発計画](../roadmap.md)に反映します。実装記録を理由にユーザーの要件を勝手に変更しません。
