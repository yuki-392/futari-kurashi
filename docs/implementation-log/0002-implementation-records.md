## 目的と対象要件

ユーザーの依頼:

> codexが実装するたびになぜこういう実装を行なっているのかを記録し、間違っている実装を私が指摘したり、後で見返せるようにしたい。

各実装の理由と指摘の履歴をMarkdownで残し、次回以降のCodexも参照する運用を用意する。今回の範囲は文書と開発ルールの追加。Phase 1の機能実装は含めない。

## 実装前の方針

作業ごとの記録、一覧、共通テンプレートを`docs/implementation-log/`に置く。`AGENTS.md`に着手前・完了時・指摘時の更新を必須ルールとして追加する。以前の環境構築は事後記録と明記して保存する。

確認条件は、READMEから一覧を開けること、各記録から理由・変更箇所・検証・指摘を確認できること、次回のCodexが関連する過去の指摘を参照する指示があること。

## 判断と理由

### D1: 作業単位のMarkdownに、固定の判断番号・指摘番号を付ける

- 採用する方法: 連番ファイルと一覧、判断D1・指摘R1などの番号を使う。
- 理由・根拠: 「0003のD1」と指定すれば、チャットを遡らずに対象と理由を確認・指摘できる。Git管理の文書なので将来のコード変更とも一緒に保管できる。
- 代案: チャットの完了報告だけに残す、1つの長い日記に追記する、外部の管理ツールを使う。
- 制約・不利益: 実装のたびに短い記録更新が必要。一覧と各記録の状態を揃える必要がある。
- 判断の状態: 採用中。

### D2: 実装前の方針、実績、ユーザー確認を区別する

- 採用する方法: 着手前に方針を書き、実装後に変更と検証を追記する。ユーザーの確認は明示された場合だけ記録する。
- 理由・根拠: 後付けの説明だけで実装理由を整理せず、方針が変わった経緯も残すため。テスト成功をユーザーの合意として扱わないため。
- 代案: 完了後だけ記録し、テスト成功時点でレビューも完了扱いにする方法。
- 制約・不利益: ユーザーが確認していない記録は未確認のまま残る。未確認であることだけを理由に、許可済みの通常作業を毎回止める運用にはしない。
- 判断の状態: 採用中。

### D3: 修正前の判断と指摘を残す

- 採用する方法: 古い判断を「変更済み」として残し、修正理由・関連記録・再検証を追記する。
- 理由・根拠: 誤った実装を指摘し、後から見返す目的に沿う。同じ指摘を次の実装で繰り返さないための参照先にもなる。
- 代案: 修正後の説明だけに書き換える方法。
- 制約・不利益: 現在採用中の判断が分かるよう、過去の記録と設計方針の両方を更新する必要がある。
- 判断の状態: 採用中。
