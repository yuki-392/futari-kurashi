## 目的と実装前の方針

承認済み計画の掃除場所・完了ごとの担当交代・今日/今週の掃除を追加する。通常ToDo・買い物・削除は対象外。既存の2アカウント・データを保持し、テスト後にcleaning-checkを既存pwa-checkへ7日間公開する。本番Hostingは変更しない。

## 判断と理由

### D1: 同じ定義と履歴を拡張

recurringTasks/recurringCompletionsへtaskType（general/cleaning）、place、rotation（fixed/alternate）を追加する。3項目がない旧文書は一般/場所なし/固定。旧文書の一括移行なし、編集時に新形式を保存する。新形式から旧形式への欠落を拒否し、履歴snapshotは変更しない。旧版画面が担当交代を省略する操作もRulesで拒否する。

### D2: 完了で交代し取消で復元

交代は2人世帯・担当1人だけ。完了実行者とは独立して現在担当以外へ交代し、履歴には完了前の担当を保存する。transactionとRulesで予定・担当・履歴の原子性を保つ。停止/再開は担当を変えず、編集は旧完了の取消を不可にする。

### D3: 週間は参考予定を計算

日本時間の月〜日。現在の未完了1件だけ操作可能。持ち越しがあれば今日完了した想定で次周期へ進み、以降の週内だけを参考表示する。担当も順に完了した想定で交代し、履歴や予定文書は先に生成しない。今週の過ぎた日を未実施履歴として補完しない。

### D4: 掃除条件と場所をサーバー側で絞る

taskType=cleaning、active=true、nextDueDate<=対象末日を条件に100件ずつ取得。場所は完全一致、任意入力の適用で購読条件に含める。選択肢一覧を作るための全件読み込みを避ける。必要なindexだけ追加する。不要購読と認証/世帯変更時の表示を破棄する。

### D5: 失敗テストと既存回帰から確認

モデル/サービス/UI/RulesでRED後に実装。Emulatorの直接改ざん・競合・文書不変性、独立2ブラウザーで交代/取消/復元/絞り込み/週間を検証。Browser plugin not availableのため既存Playwrightを使う。対象フローは家事→掃除登録→相手へ反映→完了/交代→履歴/取消→週間表示。check・integration・pwa成功後にRules/indexを反映しREADY/ソース一致を読み戻す。本人結果なしでは完了としない。

### D6: Rulesの評価回数上限への対応

既存の月末継続完了テストが1000式の評価上限で拒否された（既存Rulesテストallow22）。周期全体の照合は作成/編集時に行い、完了は定義側のサーバー時刻による次回計算、取消は改ざん不可の履歴の復元、停止再開は変更項目制限で検証する。履歴側では定義の版変更・完了操作・参照・次回日付の一致を必須にし、定義側と同じ日付計算の再実行は省く。定義の更新を伴わない履歴だけの作成は引き続き拒否する。周期・時刻の検証自体は緩めず、既存/新規の月末と不正日付テストで再検証する。
