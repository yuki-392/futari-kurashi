## 目的と実装前の方針

承認済み計画に従い、確認済みメールの2人が世帯を作成・招待・参加できるようにする。今回の範囲はローカル実装と自動検証まで。クラウド設定、ルールのデプロイ、Hosting公開、実機確認を行わない。

## 判断と理由

### D1: 所属と招待の整合性をRulesと原子的更新で保証する

UIだけでは改ざんや競合を防げないため、本人の所属・世帯メンバー・招待消費を一括更新し、getAfterで整合性を検証する。1アカウント1世帯、最大2人。参加前の世帯ドキュメント読み取りは許可せず、確認用の世帯名を招待に持つ。招待と本人所属を読むtransactionから世帯には読み取りなしでarrayUnion更新する。

### D2: 指定メールと128bitコードの両方で招待する

短い番号の総当たりを避け、Web Cryptoの128bit乱数を使用する。コードだけでは対象外の人は参加できない。24時間・1回限りとし、世帯の有効招待IDを再発行/取消で切り替える。専用バックエンド、メール自動送信、課金サービスは追加しない。古い招待文書は残るが有効招待IDと時刻で使用を拒否する。

### D3: 世帯の権限テストを今回実装する

ロードマップでは権限が別項目だが、世帯機能を全拒否や開放ルールで実装しない。今回必要なパスだけ厳密に許可し、今後の家事などのパスは全拒否を維持する。JDK 21をGit対象外のローカル専用ディレクトリに用意し、システムJavaを変更しない。

### D4: 所属の購読は認証に連動する

確認済みユーザーにのみ世帯UIを表示し、UID/認証変更で購読・表示を破棄する。未所属・確認中・所属済み・エラーを区別する。Firestore永続オフラインキャッシュは使わない。

## 実装予定と検証方法

- 機能単位でUI・Provider・サービス・型・テストをまとめる。失敗するテストから実装する。
- Rules: 未認証、未確認、他世帯、対象外メール、期限境界、失効、消費、3人目、二重所属、直接改ざん、競合を検証。
- ブラウザー: Auth/Firestore Emulatorと独立した2ユーザーで作成・招待・確認・参加・同期・再読み込み・ログアウト表示消去を検証。
- npm run check、既存Auth/PWAテスト、世帯/Rulesテストを実施。CIと関連文書を更新する。

## 実装中の追加判断

### D5: 保存の確定を待って表示し、招待確認にもトランザクションを使う

Firestoreのローカル反映だけを保存完了と見なさず、pending writesを除外しmetadata更新も購読する。対応する回帰テストの失敗→成功を確認した。ブラウザーで招待確認が拒否されるケースを調査し、同じ本人認証・同じ招待に対して単発REST取得は成功することを確認したため、確認処理もサーバー読み取りtransactionに統一する。参加時は別transactionで再検証し、確認後の取消や期限切れを防ぐ。変更後のブラウザー検証は成功。時刻条件の追加整理はD8を参照。

### D6: テスト依存の監査結果を既存課題として追跡する

@firebase/rules-unit-testing 6.0.0を追加。npm auditは12件（high 8、moderate 4）で、既存Firebase依存の警告が追加したテストパッケージにも伝播している。推奨fixはFirebase SDK/CLIやテストライブラリのメジャーダウングレードを含むため、forceは実行しない。今回の追加はテスト専用で、ブラウザーへテストライブラリを配信しない。

### D7: SDKの診断ログに招待コードを残さない

Firestoreのデフォルト警告に文書パス＝招待コードが含まれることを架空データのブラウザーテストで確認した。アプリのFirestoreログレベルをsilentにし、失敗は画面内の共通案内で扱う。設定の回帰テストを先に失敗させてから修正し、ブラウザーのコンソールにもコードが出ないことを検証する。テスト用Nodeクライアントの拒否ログは架空データのみ。

### D8: 招待の時刻検証を作成時と利用時に分ける

新規招待を同じ接続から読む追加テストで、createdAt <= request.timeの下限条件が拒否を起こすケースを確認した。作成時にはcreatedAt == request.timeを強制し、利用時にはrequest.time < createdAt + 24hだけを判定する。利用時の下限条件は削除したが、クライアントが将来時刻を登録・変更する操作は元からRulesで拒否するため、期限の延長は許可しない。発行・読取・取消を同じ接続で繰り返す回帰テストを維持する。
