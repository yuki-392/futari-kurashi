## 目的と実装前の方針

承認済み計画に従い、既存Rulesと13シナリオを維持し、2世帯の隔離とクライアントSDKの直接操作に対する検証を追加する。今回はローカルのみ。Firestoreクラウド準備・デプロイ・Hosting公開・実機確認は行わない。

## 判断と理由

### D1: 正常な2世帯を使い、権限表とテストを対応させる

作成者・参加者・他世帯・未所属・未確認・未認証を区別し、単体取得・一覧/検索・作成・更新・削除を確認する。対象メール本人に招待の事前確認を許す例外を明示する。既存世帯の所属者でも自分宛ての招待は確認できるが、参加や所属の変更はできない。Rulesの無効化はデータ準備・結果確認だけに使い、検証操作はクライアントSDKで行う。

### D2: 拒否の理由と保存後の不変性を確認する

単なる例外では通信障害やテストの不備を権限拒否と誤認するため、permission-deniedを検証する。拒否前後の全関連文書を比較し、原子的更新の分解・改ざんで部分保存が起きないことを確認する。

### D3: 競合は勝者と敗者の両方を確認する

成功件数に加え、敗者の拒否理由・所属・人数・招待消費・有効招待を照合する。時刻はEmulatorのテストデータで調整し、24時間待機しない。見つかった問題は失敗する回帰テストを残し、Rulesだけ最小修正する。API・保存スキーマ・画面は変更予定なし。

## 検証予定

- 既存13シナリオ、権限表、複数世帯、必須/型/余分な項目/時刻/UID改ざん、部分更新、確認後失効、同時作成/参加/取消/再発行を確認。
- npm run checkとnpm run test:integrationを実行し、既存CIでも追加分が動く構成を維持。
- 設計、権限表・検証手順、ロードマップ、記録一覧を更新する。

- 作成者/参加者・他世帯の作成者/参加者・招待対象者・招待作成者・メール未確認・未認証の8立場を使用し、A/B両方向を検証。本人所属の取得、コレクショングループを含む一覧/検索、未実装パスの全操作を確認。

### テスト先行と修正の証拠

1. Rules未変更で追加テストを実行し、タブを含む招待先メールの保存が成功してしまい、期待する拒否テストが失敗した。
2. 正規表現を修正後、不正メール拒否と正常発行が成功。
3. 保存結果ヘルパーの初期版で、withSecurityRulesDisabledがコールバックの戻り値を返さないことにより、競合後の検証が失敗。結果を外側に保存し、非空のスナップショットを必須とする形へ修正した。
4. 修正後の22シナリオで、実文書を使う前後比較と競合後の整合性確認がすべて成功した。ヘルパー修正前の前後比較は検証実績として数えていない。

## 実装中の追加判断

### D4: 招待先メールの空白判定をRulesでも行う

追加した直接書き込みテストで、タブを含む招待先メールが拒否されず、テストが失敗した。既存の正規表現は半角スペースだけを除外していたため、タブ・改行などの空白も除外する正規表現へ最小修正する。画面の検証を迂回した不正データの作成を防ぐ修正で、API・保存スキーマの変更はない。
