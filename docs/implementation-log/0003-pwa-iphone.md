## 目的と対象要件

[製品仕様](../product-spec.md)のPWA対応とiPhone優先の要件に対し、ホーム画面への追加・起動・再起動・更新を確認する。専用FirebaseプロジェクトのSparkプランとHostingの検証URLを用意する。Authentication・Firestore・ログインなど、次の項目の機能は含めない。

## 実装前の方針

既存のmanifest・アイコン・静的キャッシュを活かす。起動時と前面復帰時の更新確認を整え、更新の適用は利用者が選ぶ。ビルド識別子を表示し、新旧ビルドを区別できるようにする。テストから実装し、PC上のService Worker・オフライン・更新検証後、同一のHTTPS URLでiPhone実機を確認する。

## 判断と理由

### D1: 前面復帰時に更新を確認し、利用者の操作で適用する

- 採用する方法: 登録後と画面への復帰時にService Workerの更新を確認する。通信できない場合は既存の静的画面を使い、次回オンライン復帰時に再確認する。
- 理由・根拠: ホーム画面からの起動や長時間バックグラウンドに置いたアプリにも更新を届け、今後の入力フォームを勝手に再読み込みしないため。
- 代案: 自動リロード、一定間隔だけのポーリング。
- 制約・不利益: 新版の適用には操作が必要。画面復帰時に確認するため、常時即時配信ではない。
- 判断の状態: 採用中。

### D2: ビルド識別子を確認画面に表示する

- 採用する方法: `VITE_APP_BUILD_LABEL`で表示を指定し、未指定時はpackage.jsonのバージョンを使う。
- 理由・根拠: ビルドAからBへの切り替えを実機でも目で確認するため。
- 代案: 開発者ツールだけでキャッシュやファイルハッシュを確認する方法。
- 制約・不利益: 識別子は公開情報になるため秘密情報を入れない。検証画面のフッターに限定する。
- 判断の状態: 採用中。

### D3: 専用のHostingプレビューチャネルを使う

- 採用する方法: 新規専用プロジェクト、Sparkプラン、`pwa-check`チャネル、有効期限7日。接続先IDをコマンドで明示する。
- 理由・根拠: HTTPSのiPhone実機検証ができ、本番公開とは分けて同じURLに新旧ビルドを配信できるため。ユーザーがこの方針を選択済み。
- 代案: PC上だけの確認、本番チャネルへの公開。
- 制約・不利益: URLを知る人は確認画面へアクセス可能。期限後は同じ検証を続けられないため、有効期限を記録する。個人データは扱わない。
- 判断の状態: 採用中。

### D4: PC検証とiPhone実機の完了を区別する

- 採用する方法: PCではPlaywright、実機はユーザーの操作結果を機種・iOSと併せて記録する。
- 理由・根拠: PCのモバイル表示はiPhoneのホーム画面追加・standalone表示の証明にはならないため。Browser plugin not availableのためPC検証は通常のPlaywrightを使用する。
- 制約・不利益: Googleログイン・iPhone操作が必要。結果が届くまでは実機未確認として扱う。
- 判断の状態: 採用中。

### 実装中の調整（Codexによる対応）

- Firebaseプロジェクトの日本語表示名がGoogle Cloud APIで拒否された（`INVALID_ARGUMENT`）。同じプロジェクトIDで英字表示名`Futari Kurashi`に変更して作成成功。アプリの日本語名は維持した。
- CLIのプレビューチャネル公開は、既定でAuth承認済みドメインを同期する。今回はAuthを対象に含めないため、`--no-authorized-domains`を明示した。
- テスト専用に追加していた未使用のuser-eventは削除し、React Testing Library・jsdom・Playwrightを使用した。
