## 目的と対象要件

[製品仕様「3. 技術スタック」](../product-spec.md#3-技術スタック)に沿って、機能を段階的に実装できる開発環境を用意する。対象はローカル環境と設定ファイル、開発ガイドまで。ログイン・世帯共有などの業務機能、Firebaseプロジェクト作成、GitHub接続、公開は含めない。

## 実装前の方針

当時の依頼は「まずは環境構築」と「企画をMarkdownに残すこと」。そのため、Firebaseの接続情報がなくても起動できる確認画面を用意し、Phase 1の機能は未実装として区別した。

## 判断と理由

### D1: 指定された技術スタックで最小限の構成を用意する

- 採用した方法: React / TypeScript / Vite / Tailwind CSS、FirebaseのSDK、PWAプラグインを導入。Node.js 24に揃え、npmのlockfileを保存した。
- 理由・根拠: ユーザー指定の構成を守り、同じ依存関係で開発を再開できるようにするため。
- 代案との関係: サーバーを持つフレームワークへの置き換えは、指定されたシンプルな構成と専用バックエンドなしの方針に合わせて採用していない。
- 制約・不利益: リポジトリで指定するNode.jsのバージョンに合わせる必要がある。依存パッケージの更新・監査は継続して必要。
- 判断の状態: 採用中。

### D2: Firebaseの未設定状態を許容し、SDKは初回利用時に読み込む

- 採用した方法: 設定値の不足・誤記を検出し、`getFirebaseServices()`でAuthとFirestoreを遅延初期化する。
- 理由・根拠: Firebaseプロジェクトを作る前でもローカル画面を確認でき、使っていないSDKを初期画面で読み込む必要もなくなるため。
- 代案: 起動直後に必ずSDKを初期化し、設定不足では起動を失敗させる方法。
- 制約・不利益: 設定が揃っていても接続成功は保証しない。実際のSDK初期化・ログインは機能追加時に確認する必要がある。
- 判断の状態: 採用中。

### D3: Firestoreは全アクセス拒否で開始する

- 採用した方法: `allow read, write: if false`。
- 理由・根拠: 世帯のモデルや権限制御が未実装の段階で、生活データを読み書き可能にしないため。[世帯メンバー以外のアクセス制限](../product-spec.md)を実装する前提にする。
- 代案: 開発用に読み書きを開放する方法。
- 制約・不利益: 認証済みでもデータ保存できない。データ機能と同時に世帯単位のルール・Emulatorでの権限テストを追加する必要がある。
- 判断の状態: 採用中。

### D4: PWAの更新は利用者が適用する

- 採用した方法: `registerType: 'prompt'`と更新通知UI。静的ファイルをキャッシュし、個人データのruntime cacheやFirestore永続キャッシュは有効にしない。
- 理由・根拠: 今後入力フォームを追加したとき、更新による強制再読み込みで入力を失うことを避けるため。データのオフライン対応は段階的に検討する要件に合わせた。
- 代案: 新しいService Workerを自動適用する方法。
- 制約・不利益: 更新の適用に操作が必要。業務データのオフライン編集・同期は提供していない。
- 判断の状態: 採用中。

### D5: 開発上の検証と実機確認を区別する

- 採用した方法: `npm run check`とCIを用意し、検証できなかった項目も[開発計画](../roadmap.md)に記載した。
- 理由・根拠: 型チェックやビルドの成功だけでは、iPhoneでの表示・PWA更新・2人の共有が動くと判断できないため。
- 制約・不利益: 今後、ブラウザー・実機・権限の検証環境を別途整える必要がある。
- 判断の状態: 採用中。
