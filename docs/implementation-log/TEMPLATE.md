# NNNN: 作業タイトル

- 作成日: YYYY-MM-DD（日本時間）
- 更新日: YYYY-MM-DD
- フェーズ: 環境構築 / Phase 1 / Phase 2 / Phase 3
- 実装状態: 計画中 / 実装中 / 実装済み / 保留
- ユーザー確認: 未確認 / 指摘あり / 確認済み
- 関連記録: 該当なし、または関連する記録へのリンク

## 目的と対象要件

どの困りごとを解決するか。製品仕様の該当見出しへのリンクと、今回の範囲・対象外を記載する。

## 実装前の方針

どのような動作にする予定か。ユーザーから見た操作例と、達成を確認できる条件を記載する。前提・未確定事項があれば明記する。

## 判断と理由

### D1: 判断の名前

- 採用する方法:
- 理由・根拠: このアプリの要件や確認したコードに結び付けて説明する。
- 検討した代案: 該当する場合に記載する。
- 制約・不利益:
- 判断の状態: 採用中 / 変更済み（変更理由と新しい判断への参照）

必要な判断の数に応じてD2以降を追加する。

## 実際の変更

実装後に記載する。着手時は「未実装」とする。

| ファイル・関数 | 変更内容         | 関連する判断 |
| -------------- | ---------------- | ------------ |
| 対象へのリンク | 実際に変えた動作 | D1           |

## 検証結果

実行したものだけ結果を記載する。失敗・未実施も残し、必要な追試を区別する。

| 検証・コマンド      | 結果                 | 確認できたこと・限界                   |
| ------------------- | -------------------- | -------------------------------------- |
| `npm run check`など | 未実施 / 成功 / 失敗 | 実際の結果と、対象に含まれない確認事項 |

## ユーザーに確認してほしい点

操作や仕様として確認・指摘してほしい点を具体的に記載する。通常の作業を毎回承認待ちにする意味ではない。

## 指摘と対応

指摘がない場合は「まだ指摘はありません」と記載する。指摘を受けたら、以下の形式で追記する。

### R1: 指摘の要約

- 受付日:
- 対象: 判断D1、画面、動作など。
- ユーザーの指摘: 元の意味を保って記録する。Codex自身の気づきは、その旨を明記する。
- 対応方針と理由:
- 修正内容・関連記録:
- 再検証の結果:
- 対応状態: 未対応 / 対応中 / 対応済み / 要確認 / 見送り
- ユーザーによる修正確認: 未確認 / 確認済み（明示的な確認がある場合のみ）

## 未解決事項・次の作業

未確定の仕様、未検証の環境、既知の問題、次回に引き継ぐこと。なければ「なし」。

## 変更履歴

- YYYY-MM-DD: 実装前の方針を作成。
- 実装、方針変更、指摘への対応、ユーザー確認などの節目を追記する。
