## 実装前の方針と判断

### D1: 定義1件が未完了1件を表す

世帯配下recurringTasksに周期/基準日/次回予定/稼働状態/版/直近完了参照を持ち、recurringCompletionsに履歴を分離。完了するまで次回予定は動かさず、専用サーバー・日々のタスク生成は不要。履歴は定義IDと更新後の版から一意に決める。

### D2: 周期をサーバー時刻で検証する

次回はmax(今回予定日,日本時間の完了日)より後の元の周期に沿った最初の日。毎週は開始曜日、毎月は開始日の日付を維持し末日に丸める。UI/サービスは日本日付を計算し、Rulesはrequest.time+9時間から独立して検証する。端末時計のずれや日付境界による拒否は入力を残して再試行案内とし、日付整合性を緩めない。

### D3: 完了/取消と履歴を原子的に更新

完了は版確認・履歴作成・次回予定・直近参照をtransactionで同時保存。取消は直近参照と完了時の版が一致する場合のみ、予定復元・履歴の取消記録・参照nullを同時保存。編集/停止/再開は参照をnullにして取消不可にする。取消後さらに過去へ戻れず、再完了は新しい版の履歴IDで残す。履歴本体の変更・削除を禁止する。

### D4: 必要画面だけを購読する

家事はToDo/繰り返し/履歴、初期はToDo。定義/履歴100件、ホームは稼働中かつ予定日が今日以前10件ずつ。1件多く取得して追加表示を判定。既存UID+世帯keyと各購読解除で他世帯の表示・入力を破棄する。

### D5: 公開は検証済みの追加だけ

現行Rules/インデックスを記録し、既存データ・インデックスを保持して追加。Rules一致・必要index READY後にrecurring-checkをpwa-checkへ7日間公開。本番Hosting・Auth・既存データの削除は行わない。Browser plugin not availableのため既存Playwrightで検証する。

### D6: 編集と取消を区別するlastAction

定義にlastAction（create/edit/pause/resume/complete/undo）を保持し、Rulesで操作ごとの原子的更新を検証する。手動の設定編集で予定を選び直すことと、履歴へ取消を記録して元へ戻すことを区別するため。編集で過去の予定へ戻しても、既存履歴を取り消したとは扱わない。

### D7: 履歴の取消可否は現行定義から判定する

表示中の未取消履歴に対応する定義をIDごとに重複なく単体購読し、版と直近参照が一致する記録だけ取消ボタンを出す。履歴の100件ごとの追加表示に伴う必要な定義だけを取得し、画面離脱で全解除する。古い履歴のsnapshotだけで取消可能とは判断しない。
